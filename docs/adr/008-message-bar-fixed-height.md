# ADR-008 訊息列固定高度（畫布大小不因訊息而變）

- 日期：2026-10-05
- 決定者：Claude Code (Claude Sonnet 5.5)（S02 實作時決定，補足 S01 規格的矛盾；使用者未被問到）
- 狀態：採用

## 背景

S01 的 `docs/ux/ux-spec.md` 第 5 節有兩句話同時出現：「所有要閱讀的訊息放在畫布下方的訊息列，不蓋在影像上」與「訊息列的高度會隨內容變化，但**畫布大小不變**，所以板子不會被擠動」。
原型是網頁，頁面可以往下長，所以兩句話不衝突。桌面程式的視窗大小固定：訊息列變高，畫布就必須變矮——除非訊息列的高度其實不變。

## 決定

訊息列**固定高度**：`docs/ux/tokens.json` 的 `sizes.messageBarHeight`（96 px）。內容放不下時在列內捲動（垂直捲軸），不撐高、不擠動畫布。
`MessageBar` 的內容有三種：常駐提示（一行）、吐司（暫時蓋過提示，4 000 ms）、卡片（標題、說明、做法清單、動作按鈕；無匹配與錯誤用）。

## 證據

事實（已觀察）：

- `tst_shell` 的截圖（`screenshotsForReview`）顯示：標題＋說明＋ 2 條做法＋ 1 個按鈕剛好放進 96 px，沒有被切掉。S01 的文案裡無匹配最多會列出更多條做法（例如樣本框到多個元件的那一條要兩行），所以有些卡片放不下，需要捲動。放不下的實際比例**沒有統計**。
- `tst_shell::messagesNeverChangeTheCanvasSizeOrCoverTheCanvas` 驗證：很長的提示、吐司、含 12 條做法的卡片、清除卡片，每一種狀態畫布與視埠大小都不變、訊息列高度不變、訊息列在畫布下方且不相交。

假設（未驗證）：

- 96 px 夠放大多數卡片的標題與第一、二條做法，使用者不必捲動就看到動作按鈕。**沒有用真實使用者驗證**；若按鈕常常在捲動區外，要調高這個數字（它在 tokens 裡，改一個數字即可）。

## 否決的替代方案

- **訊息列高度隨內容變化、畫布跟著變矮**：違反 S01 的「板子不會被擠動」。使用者回饋的原始問題是訊息擋住料件；畫布忽大忽小同樣會讓檢測員跟丟。
- **訊息蓋在影像上（半透明）**：使用者在 S01 明確否決。
- **彈出視窗**：打斷操作；無匹配與提示是常態，不是例外。

## 後果

- S04 的 `IMessageView` 實作要遵守：訊息只進 `MessageBar`，不新增蓋在畫布上的元件（「空白」卡片是唯一例外，因為那時畫布上沒有東西可擋）。
- 若之後要放進度條與〔取消 (Esc)〕（S04），它們必須擠進同樣的 96 px。
