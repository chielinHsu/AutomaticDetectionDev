# ADR-016 OpenCV 搜尋：由粗到細的 NCC、小的分數圖自己算、和 JobRunner 共用執行緒數

- 日期：2026-10-06
- 決定者：Claude Code (Claude Opus 5.5) 提出並實作（S07）。依據是本步驟的測試與量測（下面「證據」）；使用者沒有針對這份 ADR 另外表示意見。調整參數（`OpenCvSearchOptions`）是起點，S10、S11 依完整的效能矩陣再調。
- 狀態：採用

## 背景

S07 要做出第一個真正看影像的 back end（`src/infrastructure/backend_opencv/`）：`ITemplateBuilder`、`IPatternSearcher` 的 OpenCV 版，以及流程 B 的 `ILibraryMatcher`。port 的契約（S03）：分數 0..1 且 ≥ `minScore`、角度在範圍內、依分數排序、中心落在區域（整張影像或視窗清單）內、可重入、不丟例外、取消是協作式的。預算（`perf/budgets.json`）：T1 範本建立 30 ms、T2a 5 MP 的種子搜尋 150 ms、T4 200 個視窗的驗證 60 ms、T6a 召回率 ≥ 99%、T6b 位置誤差 ≤ 0.5 px。計畫寫「由粗到細、角度掃描、視窗清單、domain 的 NMS、拋物線次像素、`cv::setNumThreads` 與 JobRunner 協調」。

## 決定

### 1. 比對方法：正規化相關係數（`TM_CCOEFF_NORMED`），由粗到細

- **範本**（`OpenCvTemplateBuilder`）：金字塔每層縮小一半，直到範本的短邊剩 8 像素（`minTopSidePx`，最多 4 次）。每一層各有一組旋轉的範本：步進讓範本的角落移動 1 像素（`cornerShiftPx`；64×32 的範本在原尺寸是 1.6°、頂層 16×8 是 6.4°）。旋轉的範本不是把裁好的矩形轉一轉（四個角會空掉）：先裁一塊含周圍影像的方形，縮小、轉過再從中間切出範本大小。
- **頂層**：每個角度一次 `cv::matchTemplate`，每個位置取最好的角度；分數 ≥ `minScore − 0.2` 的局部最大值是候選，先做一次 NMS。影像切成幾條橫帶平行，記憶體只要每條帶一張分數圖。
- **往下每一層**：每個候選在換算過來的位置 ± 2 像素、上一層的角度 ± 一步之內再比；最好的點在範圍邊上時往那邊移（爬坡，位置最多 3 次、角度到兩側都比過為止）。
- **第 0 層**：位置用三點拋物線內插到次像素；角度也用相鄰兩個角度的分數內插（兩側的角度沒比過就補比；在角度範圍的一端時，用往內的三個角度，夾在範圍內）。角度的誤差約是第 0 層角度步進的 0.2 倍（範本角落位移約 0.2 像素）。
- **合併**：最後用 domain 的 NMS（範本大小的旋轉矩形、IoU > 0.5，和 use case 同一個規則）。
- 座標：金字塔的換算 `x_l = 2·x_{l+1} − 0.5`（`OpenCvPyramid.h`），OpenCV 的像素中心在整數座標、ADR-010 在 +0.5，旋轉用 `cv::getRotationMatrix2D`（正的角度在螢幕上逆時針，和 ADR-010 相同）。

### 2. 小的分數圖自己算（`OpenCvCorrelation`）

精修時每個候選只比幾十個位置。這種大小的分數圖改用直接的點積：`Σ T'·I' ＝ Σ T·I − ΣT·ΣI ／ n`（8 bit × 8 bit 的整數點積），視窗的 ΣI、ΣI² 用積分影像（同一塊影像比好幾個角度時共用），範本的 ΣT、ΣT² 在建範本時算好。定義和 `TM_CCOEFF_NORMED` 相同（平的視窗或平的範本給 0）。判斷：分數圖的位置數 × 範本像素數 ≤ 4 × 10⁶ 時自己算，否則用 `cv::matchTemplate`（頂層的整張影像走 DFT 比較快）。

### 3. 灰階與位元數

搜尋器只比 8 bit 灰階：`Gray8` 零複製；`Gray16` 以 `v × 255 ／（2^位元數 − 1）` 換算（位元數是 `effectiveBits`，含使用者的覆寫，ADR-014 的 S07 後續）；彩色轉灰階。換算是一次複製並計數（ADR-014 規則 6）。視窗清單只轉換視窗附近的像素。

### 4. 執行緒

頂層的橫帶、精修的候選、視窗清單的視窗用 `cv::parallel_for_`（OpenCV 自己的池，巢狀的會在呼叫的執行緒上依序執行）。執行緒數：組裝根在建立 OpenCV back end 時 `cv::setNumThreads(核心數 − 1)`，和 JobRunner 的 worker 數相同（`app::workerThreads()`，保留一個核心給 UI）。latest-wins 時只有一個搜尋在跑，被取代的舊搜尋在下一個檢查點（每一個角度、每一個候選）就停，所以兩個池子不會同時把每個核心佔滿。

### 5. 流程 B（`OpenCvLibraryMatcher`）

每個候選類型用參考影像整張建範本（校正值不同時先縮放成板子的比例），在區域裡找（區域當成一個視窗）；所有類型的匹配依分數合併成元件（交集 ÷ 較小的框 > 0.5 是同一個元件）。唯一的預篩選是「參考影像比區域大就不比」。範本每次重建（不快取）。

## 證據

- 準確度（`tst_opencv_backend`、`tst_opencv_end_to_end`、`perf_opencv` 的 T6）：合成板子 8 種情況、5 MP、共 6 673 個元件，召回率 100%、位置誤差 p95 0.11 px、最大 0.50 px（反光的元件）；角度的正負號（±3°、+4.5°）誤差 < 0.35°；三種正規格式的結果相同。
- 「兩側的角度沒比過就補比」與「範圍一端的內插」都是測試先失敗才加的：沒有補比時，乾淨板子上每個元件的角度都是 −1.0°（格點沒有 0°、最好的 −1° 在已比的角度的邊上，沒有兩側可以內插）；沒有一端的內插時，+4.5° 的板子給 5.0°。
- 角度的準確度（`tst_opencv_backend` 的角度掃描）：48×28 的範本、±5° 每 0.5° 一組，最大誤差 0.42°（第 0 層步進 2°；範本角落位移 0.21 像素）；±30° 每 2.5° 一組，最大 0.21°。誤差的來源是 NCC 對角度的曲線在真值兩側不對稱（真值 +1° 時，−1° 與 +3° 的分數是 0.981 與 0.966），拋物線的頂點偏向 0°。試過「每個角度用自己的次像素峰值再內插」，最大誤差只從 0.424° 變 0.411°，沒有採用。
- 變異測試（14 個）：13 個被抓到；**角度的爬坡（旁邊的角度更好就移過去）拿掉之後，所有測試結果都一樣**（±5°、±30° 的掃描誤差完全相同）——補比兩側已經足夠。爬坡留著當防禦（上一層的角度估計差兩步以上時才有作用，沒有重現過）；位置的爬坡沒有做變異。
- 自己算小分數圖（同一台機器、同一份板子，改之前 → 改之後，各 1 次的中位數）：T2a 193 → 64 ms（精修 224 → 36 ms）、T4 87 → 30 ms、use case 總時間 228 → 79 ms；找到的元件完全相同（`tst_opencv_backend::directCorrelationMatchesOpenCv`：和 `cv::matchTemplate` 的差 < 10⁻⁴）。
- 執行緒（T2a 的情境，中位數，3 次的範圍）：1 個 126–133 ms、2 個 75–84、4 個 65–83、8 個 53–58、15 個 50–57 ms。
- 真實影像（使用者提供的 24.4 MP、12 bit 兩張）：整個 use case 113–205 ms；找到的針腳見 `docs/steps/S07-opencv/perf.md`。
- 最終 3 次（`perf.md`）：T1 p95 0.34–0.47 ms、T2a 67–72 ms、T4 31–33 ms、T6a 100%、T6b p95 0.106 px，都在預算內。

## 否決的替代方案

- **每一層都用 `cv::matchTemplate`**：最簡單，但精修的分數圖只有 5×5，`matchTemplate` 仍走 DFT，固定成本主宰（T2a 超過預算，見證據）。
- **整張影像在每一層都比**（不精修）：每一層都要全部的角度，成本隨角度數成倍增加，頂層之下沒有必要。
- **用遮罩的 `matchTemplate` 處理旋轉範本的四個角**：OpenCV 的遮罩版本比較慢，而且從影像裁周圍的方形就沒有空白的角。
- **形狀比對（輪廓、邊緣方向）**：對光照比較不敏感，但那是 HALCON 的 shape model 的領域（S08），S07 先做計畫指定的強度相關法，S09 用 A/B 比較兩者。
- **OpenCV 用全部的核心、JobRunner 也用全部的核心**：舊搜尋還沒停的那幾毫秒會超額訂閱；把兩個數字綁在同一個函式，之後改一處就好。

## 後果

- 強度相關法的已知限制（`docs/steps/S07-opencv/spec.md`）：對光照變化、反光、縮放敏感；相似但不同的東西（例如真實影像裡焊墊的邊緣）可以有 0.7–0.85 的分數；範本有一部分在影像外的元件找不到；角度範圍越大越慢（±180° 是 ±5° 的 4 倍）。
- `OpenCvSearchOptions` 的預設值（頂層分數少 0.2、精修 ± 2 像素、頂層短邊 8 像素、每個視窗最多 4 個候選）是合成板子與兩張真實影像定的起點。
- 流程 B 的成本隨候選類型數 N 線性成長（約 9 ms／類型，`perf.md` 的 T7）；快取範本（ADR-006 §7.3）與依外形預篩選（§7.2）是之後的優化，UI 也還沒接（使用者決定 S07 不接）。
- `cv::setNumThreads` 是整個程式共用的設定：只在建立 OpenCV back end 時設定，只用 fake 時不碰它。

## 後續（2026-10-15）：比對區、遮罩、邊緣（ADR-028）

- 範本裁比對區；範本記住 `originOffset`（主體中心 − 比對區中心），搜尋器最後才換成主體中心；視窗的邊距與頂層的 `reach` 多加 `|o|`；NMS 的框是比對區大小、在範本中心。整框時 `o ＝ 0`，程式路徑相同。
- 遮罩：每層每角度一張；大的分數圖 `cv::matchTemplate(TM_CCOEFF_NORMED, mask)` 之後，非有限值與 `|s| > 1 + 1e-3` 設 0（不能夾成 1）；小的分數圖自己算 `correlateMasked`；遮罩蓋住外接矩形 ≥ 95% 當矩形；某層剩不到 32 個像素就不用那一層。
- 邊緣：每一層各自 Sobel 3×3 大小 × `edgeScale`（0.25，8 bit 的階梯邊緣大小約 1020），之後才旋轉與裁切。
- 小範本（例如 37 × 27）金字塔只有 2 層，粗搜比整框慢；這次不先優化，真實影像的時間見 ADR-028 的量測。
