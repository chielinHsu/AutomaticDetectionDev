# ADR-002 復原模型：Command ＋ 三個範圍（提案、類型編輯、文件）

- 日期：2026-10-05（同日修訂：新增「類型編輯」範圍，見 ADR-006）
- 決定者：Claude Code (Claude Sonnet 5.5) 提出，S01 的原型實作並驗證；使用者於 2026-10-05 確認採用（含「接受或捨棄後復原回到 Preview」與「`Esc` 捨棄提案不跳確認」）
- 狀態：採用

## 背景

總體計畫的 UX 原則「永遠可以反悔：所有修改走 Command」。自動產生的結果一定有錯，修正要便宜。S04 要實作復原／重做，預算 I6：復原一次 1 000 框的 commit ≤ 50 ms。

限制：`application` 層不能 include Qt（`docs/architecture.md`），所以不能用 `QUndoStack`。

使用流程裡有三種不同的「修改」：

1. 對**已接受的文件**（板子上的元件）的修改：移動、刪除、補一個、接受。
2. 對**尚未接受的提案**的修改：預覽時刪除一個元件、補一個、改選另一個樣本。提案隨時可能被新的搜尋取代。
3. 對**元件類型**的修改（類型編輯器）：畫框、改矩陣、加檢測窗。尚未儲存的草稿不該污染文件的歷史，但儲存這件事本身要能復原。

## 決定

**Command 模式，純 C++ 的 `UndoStack`（application 層），分三個範圍：**

| 堆疊 | 範圍 | 內容 |
|---|---|---|
| `ProposalSession` 的堆疊 | 目前的提案（`Preview` 狀態） | 刪除元件、補一個、移動、改選樣本 |
| `TypeEditSession` 的堆疊 | 類型編輯器的草稿（`EditingType` 狀態） | 畫框、移動／縮放框群組、改列數／欄數／間距／比例、加窗、刪除 |
| `InspectionDocument` 的堆疊 | 已接受的文件與樣本庫 | 對板上元件的修改、**Accept**、**Discard**、**儲存元件類型**（板子複本，可選同時存入樣本庫）、**從樣本庫更新**、**存入樣本庫**、刪除樣本庫條目 |

規則：

1. **`Accept` 與 `Discard` 是文件堆疊上的 Command**，各自帶著當時提案的快照（提案物件、提案堆疊、門檻）。復原它們，狀態回到 `Preview` 並還原提案（狀態機事件 `UndoToPreview`）；重做再接受或捨棄一次。
2. **「儲存元件類型」是文件堆疊上的一個 Command**（帶著儲存前、儲存後的類型內容；若同時存入樣本庫，庫條目的前後內容也在同一個 Command 裡）。〔從樣本庫更新〕、〔存入樣本庫〕、刪除庫條目也各是一個 Command（ADR-006 §5：庫與板子是複本關係，兩邊只透過這些明確動作同步）。復原它**不會**重新開啟編輯器，只把類型改回去，板上所有同類型元件跟著還原。草稿的堆疊在儲存或取消時丟棄。
3. 新的搜尋結果進來，建立新的 `ProposalSession`（舊堆疊清空）。
4. `Accept`／`Discard` 執行時，先清掉提案堆疊的「可重做」部分。否則復原回 `Preview` 後 `Ctrl+Y` 會先重做殘留的舊動作，而不是重新接受。（原型測試抓到這個缺陷，已修正。）
5. `Ctrl+Z` 的對象依狀態決定：`EditingType` → 草稿堆疊；`Preview` → 提案堆疊，不會越過去動文件歷史；`Idle` → 文件堆疊。`Searching`、`DrawingRegion` 時忽略。
6. **不進堆疊**：縮放、平移、選取、工具、分數門檻、back end 切換、主題。理由：它們不改變使用者的成果；門檻是對快取候選重新過濾，可隨時拖回。
7. 連續拖曳是**一個** Command（按下到放開），不是每一個滑鼠移動事件一個。表單欄位的輸入也一樣：從取得焦點到離開（`change`）才算一個 Command，輸入過程中即時預覽但不進堆疊。
8. 一個 Command 對應一個使用者意圖：刪除 N 個元件是一個；接受 N 個元件是一個；「一次產生標準檢測框」是一個。
9. 堆疊深度上限 200，超過丟棄最舊的（同時釋放它帶的快照）。開啟另一張影像時清空兩個堆疊，並在有未接受的提案或未儲存的物件時先確認。
10. 「是否有未儲存的修改」＝堆疊目前位置是否等於上次儲存時的位置。類型編輯器有自己的「有未儲存的修改」：`Esc` 在有修改時**不會**直接丟棄草稿，要按〔取消〕確認。
11. `InspectionDocument` 每個 Command 只發出**一次**變更通知（批次），不是每個物件一次。這是達成 I6 的前提。

## 證據

- 事實：S01 的互動原型（`docs/steps/S01-ux-spec/explainer.html`）實作了這個模型，並以頁內腳本驗證：刪除／復原／重做、移動只產生一個 Command、接受後復原回到 `Preview` 且文件清空、再重做回到 `Idle`、捨棄後復原、`Preview` 中多餘的復原不會動文件歷史、類型編輯器草稿的復原、儲存類型後復原使板上 3 顆 IC 從 33 個框回到 41 個、有修改時 `Esc` 不丟棄草稿。上述每一項在最後一輪都通過（最終版 124 項斷言）；另外驗證了庫與板子複本的同步動作都可復原：從樣本庫更新後 `Ctrl+Z`、存入樣本庫、刪除庫條目後 `Ctrl+Z`。
- 事實：測試抓到並修正了規則 4 的缺陷（修正前，接受後復原再重做，會先重做殘留的「補一個」）。
- 參考：TRI 手冊 §4.9.2.7「全部關閉」在有未儲存的元件庫時會詢問儲存／不儲存／取消，與規則 10 的精神一致；TRI 手冊 §3.1.2 存檔時有備份檔（`*.pre.bak`）。
- 假設（未驗證）：復原 1 000 框的 Command 能在 50 ms 內完成。原型是瀏覽器 DOM，不能代表 Qt；S04 要量 I6。

## 否決的替代方案

- **`QUndoStack`**：application 層不能依賴 Qt。
- **每一步存整份文件快照**：實作最簡單，但每次修改都複製全部物件，成本隨物件數與堆疊深度成長；而且沒有「一個意圖一個 Command」的標籤與合併。
- **單一全域堆疊，連「搜尋結果進來」與「編輯草稿」都是 Command**：每次調參重新搜尋、每次改一格欄位都會多一步，`Esc` 與復原的語意混在一起，使用者按 `Ctrl+Z` 會莫名其妙回到上一份提案，或丟掉還沒儲存的類型。
- **接受後復原只移除物件、回到 `Idle`，提案不保留**：較簡單，但誤按 `Enter` 後要重新框樣本、等搜尋，修正不便宜，違背「永遠可以反悔」。代價是堆疊裡的 Accept／Discard 帶著提案快照，佔記憶體，深度上限與最舊先丟可限制它。

## 後果

- S04 的 `InspectionDocument`、`ProposalSession`、`TypeEditSession`、`UndoStack` 都放 application 層，無 Qt。每個 Command 要有「撤銷後等於原狀」的單元測試。
- 狀態機要多處理 `UndoToPreview`（`Idle` → `Preview`）。見 `docs/ux/ux-spec.md` 第 6 節。
- `Esc` 捨棄提案不需確認對話框，因為可復原。
- 如果使用者回饋不要「回到 Preview」，改成「回到 Idle 並丟棄提案」只影響規則 1 與 `UndoToPreview`；其餘規則不變。那時要新增一筆 ADR 取代本筆。
