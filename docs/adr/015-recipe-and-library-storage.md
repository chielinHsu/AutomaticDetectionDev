# ADR-015 配方與樣本庫的儲存：有版本的 JSON、原子寫入、TRI 的分層

- 日期：2026-10-06
- 決定者：樣本庫的分層由**使用者決定照 TRI 的做法**（S06 session，2026-10-06；先另開 session 圖解我的建議與 TRI 的差異，再選 TRI）。「這一步不接存檔 UI，但存檔與開啟是必要功能，要記在待辦」也是使用者決定。檔案格式、版本、原子寫入、背景存檔由 Claude Code (Claude Opus 5.5) 提出並實作。
- 狀態：採用（schema 是 v1；S12 的匯出步驟「定案 schema」時可以升版，舊檔由遷移讀進來）

## 背景

S03 定了 port：`IRecipeStore`（save／load 一份 `Recipe` ＝ 板子＋搜尋參數）與 `ILibraryStore`（loadAll／find／save／remove），契約寫「損壞的檔案回 FormatInvalid，不當機也不丟例外」。S06 的計畫要求：JSON 實作（Qt Core）、`schemaVersion` 與遷移掛勾、非同步寫檔；v1 的範例檔要永遠讀得進來。S01 修訂要求樣本庫儲存（Project＋User 兩層、料號與別名索引）與板子（元件實例＋用到的類型複本，`libId`）的儲存。

文件之間的衝突：ADR-006 §4 建議「Project＋User 兩層」，ux-spec 第 14 節 #12 建議「只做使用者層，板子的複本相當於專案層」。兩份都寫「S06 定案」，所以問了使用者。

## 決定

### 1. 檔案格式（`infrastructure/storage/JsonCodec`、`JsonFile`）

- UTF-8 的 JSON，縮排（可以比對、可以人工檢查）。頂層是物件，帶 `"format"`（`"aoi-recipe"`／`"aoi-library"`：拿錯檔案會被認出來）與 `"schemaVersion"`（正整數）。開頭的 UTF-8 BOM 略過（記事本存過的檔案）。
- **每個欄位都寫**（包括用不到的，例如 Body 群組的 matrix），`load(save(x))` 才能還原出完全相同的內容。浮點數逐位元相同（Qt 的最短往返表示）；**唯一的例外是 −0.0 讀回來是 +0.0**（JSON 不分正負零，數值相等），寫進 `IRecipeStore` 的契約。
- 列舉寫成小寫英文字串（`"found"`、`"pin"`），不寫數字。長度單位照 domain：類型與框群組是 µm（欄位名稱以 `Um` 結尾），元件位姿是影像像素。
- 參考影像：`{width, height, format, umPerPixel, encoding: "base64", data}`，像素逐列緊密排列（`Gray16` 是小端），**不壓縮**直接 base64；沒有參考影像寫 `null`。大小限制單邊 ≤ 16384、≤ 256 MiB，解出來的 byte 數要剛好等於寬 × 高 × 每像素 byte。
  - **為什麼不壓縮**：第一版用 `qCompress`／`qUncompress`。Debug 的測試抓到 **Qt 6.8.0 的缺陷**：`qUncompress` 遇到被截斷的壓縮資料會撞上 `Q_UNREACHABLE`（`qbytearray.cpp` 第 680 行，Debug 直接中止；Release 沒有當機只是碰巧，那是未定義行為）。一個壞掉的配方檔不可以讓程式當掉，所以不呼叫它。參考影像是樣本的小裁切，不壓縮的代價可以接受；之後真的嫌大，再換一個能安全處理壞資料的解壓器（`encoding` 換新值、升版）。
- **讀的時候嚴格**：缺欄位、型別不對、列舉不認得、數字不是有限值、整數不是整數或超出範圍、id 重複、元件參照不存在的類型 → `FormatInvalid`，訊息帶 JSON 路徑（例如 `board.components[12].pose.x must be a number`）。不認得的多餘欄位略過。
- **寫的時候檢查存不存得下**：非有限的數字、不是合法 UTF-8 的字串、元件參照不存在的類型、id 重複 → `InvalidArgument`，不寫檔（寫得出去、讀不回來的檔案比沒寫更糟）。

### 2. 版本與遷移

- `save` 一律寫這個程式的目前版本；`load` 逐版升級（`migrations[k − 1]` 把 k 版的 JSON 改成 k + 1 版，改 JSON、不改 domain），比目前版本新的檔案回 `FormatInvalid`（訊息說是較新的程式寫的）。`Recipe::schemaVersion` 在讀進來之後是檔案原本的版本。
- v1 是第一版，沒有遷移；機制用注入的假遷移測試（順序、每升一版更新 `schemaVersion`、缺少或失敗的遷移）。
- **v1 範例檔** `tests/infra/fixtures/recipe-v1.json`、`library-v1.json` 是手寫的，**不要改**：之後的每一版都要讀得進來（測試逐欄位檢查）。

### 3. 原子寫入

- `QSaveFile`：先寫暫存檔，全部成功才換名。資料夾不存在、目標唯讀、磁碟滿 → `IoFailed`，舊檔案原封不動，不留暫存檔（測試驗證）。
- 同一個路徑同時存幾份：磁碟上留下其中完整的一份；Windows 上兩個換名撞在一起時，有的呼叫回 `IoFailed`（實測 30 次裡約 7 次）。要「依序、留下最後交出的那份」用下面的 `RecipeSaver`。

### 4. 背景存檔（`application/document/RecipeSaver`）

- 「非同步寫檔」的做法：port 維持同步（容易測、容易推理），由 application 的 `RecipeSaver` 把存檔排到 `IExecutor` 的 worker 上。`save()` 立刻回傳編號；同一個路徑同時只寫一份，寫的時候又交進來的排在後面，**還沒開始寫的舊存檔被更新的取代**（它的 done 收到 `Cancelled`）；不同路徑可以同時寫；done 在 worker 執行緒上，每個編號恰好一次；解構時等所有存檔寫完。
- 呼叫端的責任（還沒有 UI，寫進註解與 plan 的提醒）：存完才 `markSaved`，而且要標在**取快照時**的文件位置；存檔期間文件又改了，文件仍是未儲存。

### 5. 樣本庫：一個檔案一層，TRI 的分層（使用者決定）

- `JsonLibraryStore`：一個檔案 ＝ 一層。條目的 id 由那一層指派（前綴＋流水號），**永不重複使用**（下一個號碼存在檔案裡）：板子的複本用 `libId` 記得來源，重複使用會讓舊板子指到別的類型。以料號辨識（去掉前後空白、Unicode 簡單大小寫折疊；`ß` 不等於 `ss`）；同料號覆寫並保留 id 與位置。存進庫的條目 `libId` 是空字串。損壞的檔案：每個呼叫回 `FormatInvalid`，而且 save、remove **不覆蓋它**。寫入失敗時記憶體內容也不變。
- `LayeredLibraryStore`（TRI，TR7700 手冊 §4.9.1、§4.9.7.1）：層的順序就是查找順序，`standard()` 是 **專案 → 使用者 → 系統**（系統層唯讀；專案層、系統層可以沒有）。
  - find：一層一層往下找，同一層先比料號再比別名，第一個找到的就回傳（上層的別名也勝過下層的料號）。
  - loadAll：所有層，同料號只留最上層的。
  - save 存到哪一層：① 已經有這個料號的最高可寫層（存完 `find(料號)` 一定回傳剛存的內容）；② 都沒有：`libId` 指到的那一層（可寫的話；TRI：「從 Project 載入的存回 Project」）；③ 其他：使用者層（TRI：「其他存到 User」；從唯讀的系統層來的也是）。
  - remove：在唯讀層 → `InvalidArgument`；id 帶層的前綴（`proj-`、`user-`、`sys-`），所以跨層不重複，`layerOf(libId)` 給 UI 顯示「專案／使用者／系統」。
  - 任何一層的檔案損壞：用到它的呼叫回錯誤（訊息帶層名），不略過（略過會讓查找悄悄換成下一層的條目）。
- 板子與庫的關係不變（ADR-006 §5）：板子的複本存在配方裡；刪庫條目不影響已存的配方（測試驗證）。

## 證據

- `tst_recipe_store`：每個欄位都不同值的配方往返逐位元相同（含次正規數、最大值、1/3、`0.1 + 0.2`、2⁵³ + 2，參考影像五種格式、子影像的 stride）；−0.0 讀回 +0.0；v1 範例檔逐欄位檢查；遷移的順序與失敗；31 種壞檔各回 `FormatInvalid` 並指出路徑；6 種不是配方的位元組；**隨機破壞 500 次**（翻 byte、刪一段、插入、截斷）全部是成功或 `FormatInvalid`；BOM；中文路徑；7 種存不下的內容不寫檔；唯讀目標時舊檔不變、不留暫存檔；6 個執行緒同時存同一個路徑。
- `tst_library_store`、`tst_library_layers`：上面每一條規則各至少一個測試（含 6 種損壞的樣本庫檔案、唯讀目標、4 個執行緒同時存）。
- `tst_recipe_saver`：store 卡住時 `save()` 照樣回來、done 在 worker 上；被取代的收到 `Cancelled`；不同路徑互不等待；錯誤與例外變成結果；解構等寫完；4 個執行緒對 3 個檔案存 600 次：每個檔案最後寫下的是編號最大的那一份、每個編號恰好一個結果、同一個檔案從來沒有兩個同時在寫。
- 量測（`perf.md`）：5 000 個元件的配方存檔約 0.1 秒（3 次的中位數 93.5–99.3 ms，另有 1 次 483 ms，原因不明）、讀檔 29–39 ms；背景存檔佔呼叫端 0.35–0.38 ms（中位數，取快照的複製）。Qt 6.12.0。

## 否決的替代方案

- **另一種分層（我原本的建議）**：專案層 ＝ 板子的類型複本（存在配方裡）、`ILibraryStore` 只有使用者層、「先板子再整個庫」交給比對範圍。檔案少一份要同步，但和 TRI 的做法不同；使用者看過圖解之後選了 TRI。
- **非同步的 port（`saveAsync`）**：port 多一個方法，測試要處理時序；同步的 port ＋ `RecipeSaver` 把非同步留在一個地方。
- **用 `JobRunner` 跑存檔**：它是 latest-wins（新工作會取消舊的），而且是搜尋共用的；存檔要依序、不能被搜尋取消。
- **一個條目一個檔案**：存一筆不必重寫整份（1 000 筆時存一筆約 0.12–0.14 秒，`perf.md`），但檔案多、id 與「下一個號碼」的一致性更難保證；v0.1 用一個檔案，數字留在 `perf.md` 當之後的依據。
- **寬鬆的讀取（缺欄位就用預設值）**：損壞的檔案會被讀成看起來正常、其實錯的配方。
- **參考影像用 `qCompress` 壓縮**：見上，Qt 6.8.0 的 `qUncompress` 對截斷的資料是未定義行為。
- **二進位格式、SQLite**：不能人工檢查與比對；SQLite 多一個依賴。現在的大小（5 000 個元件約 2 MB）JSON 足夠。

## 後果

- **存檔與開啟配方的 UI 還沒有任何一步涵蓋**（使用者決定這一步不接，記在 `docs/current-status.md` 的待辦）。要開啟配方，v1 還缺**影像的路徑**（`Board` 只有 `name`，是影像的檔名）：加上去要升 schema 版本並寫一個遷移。
- 分層的庫還沒有組裝進程式（沒有 UI 用它）：專案層的檔案放哪裡（建議：配方所在的資料夾）、使用者層（建議：`QStandardPaths::AppDataLocation`）、要不要有系統層，接 UI 的那一步決定。
- 樣本庫第一次呼叫時讀檔、之後用記憶體的內容：另一個程式同時改同一個檔案，這裡不會知道（v0.1 的限制）。
- S07 的 `ILibraryMatcher`：候選清單由呼叫端挑（ADR-006 §7）；用 `LayeredLibraryStore::loadAll()` 就是 TRI 順序、上層遮住下層之後的清單。
