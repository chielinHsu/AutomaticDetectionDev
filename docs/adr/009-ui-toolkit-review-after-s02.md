# ADR-009 S02 實測後重審 UI 工具集（ADR-001 的重審條件）

- 日期：2026-10-05
- 提出者：Claude Code (Claude Sonnet 5.5)（整理證據與選項）
- 決定者：**使用者**（待決定）
- 狀態：**提案（待使用者決定）**。在使用者決定之前，ADR-001 照舊有效；這份**不取代**ADR-001。

## 背景

[ADR-001](001-ui-toolkit.md) 說：S02 量測若在批次繪製與縮放簡化都做完後，I1（5 000 框）p95 仍 > 16.7 ms，且 profiler 顯示瓶頸在繪製，才新增 ADR 重審；沒有這個證據不推翻。
S02 做完了批次層（`RoiLayerItem`）與縮放簡化（LOD），並依實測把框的畫法從 cosmetic 描邊改成整數像素的填色細矩形。結果見 [`perf.md`](../steps/S02-ui-shell/perf.md)。

## 證據

事實（已觀察，同一台機器；方法與限制見 `perf.md`）：

- I1 p95，offscreen（Qt 軟體光柵化，不含顯示）：同一份程式 13 次執行落在 **14.1–20.7 ms**，其中 7 次 ≤ 16.7；中位數 6–9 ms。
- I1 p95，**真實視窗**（windows 平台，含後端緩衝呈現）：**22.1 ms**，中位數 13.2 ms；每幀多出約 6 ms 的固定成本。
- I1 p95，視埠 1600×900（offscreen）：21.3 ms。20 000 個框、視埠 1000×700：15.7 ms。
- **瓶頸在繪製，而且有數字**：5 MP 影像只占 0.4–1.8 ms；事件處理（`zoomAt`）0.4 ms；框層在縮放 0.35–0.5 時 9–14 ms，那時 2 580–3 133 個框的 Pin 與窗剛好超過 3 px，全部要畫，每個框 8 個細矩形，每個矩形約 0.28 µs。
- 已做的優化：描邊 → 填色細矩形（純 QPainter 微基準 18–22 ms → 4.5–4.9 ms，約 4 倍；I1 p95 約 50 → 15–21 ms）。自己把矩形寫進 ARGB 緩衝只再快 1.5 倍，沒有採用。
- 其餘 UI 預算都通過，餘裕大：U1a p95 5.9 ms、U1b 10.5 ms、U4（BMP／PNG／JPEG）47／142／88 ms、I2 1.5 ms、I5 6.4 ms；真實視窗的 U1b 26 ms、I2 3.9 ms、I5 10.5 ms 也通過。

假設（未驗證）：

- GPU 路徑（`QOpenGLWidget` 視埠，或 QML 場景圖）能把「三千多個細矩形」和「每幀的呈現成本」都降下來。**沒有在本專案量過**；要量得準需要一個能等到 GPU 完成的量法（`sendPostedEvents` 只量到 CPU 這一端）。
- 「縮放時先縮放快取的點陣圖、停下來再重繪」能讓縮放幀變便宜，代價是縮放途中畫面是糊的。沒有量過。
- 使用者實際上會不會常常在縮放 0.35–0.5 這個最貴的區間連續縮放，沒有資料。

## 選項

| 選項 | 內容 | 代價與風險 | 能不能量 |
|---|---|---|---|
| **A. 維持 Widgets＋軟體光柵化，S11 再優化** | 現狀。S11（先量再改）處理：縮放時快取、必要時直接寫像素、改善 LOD 規則 | 最便宜；I1 在真實視窗仍可能超標，直到 S11 做完 | 已經有基準線 |
| **B. 仍用 Widgets，換 `QOpenGLWidget` 視埠** | 幾行程式；ADR-001 原本就列為備案 | 要驗證驅動與 GPU 差異；量測方法要改；CPU 繪製路徑（`QPainter`）在 GL 下行為不同，要重看畫法 | 可以在 S11 試，用真實視窗量幀率 |
| **C. 換 QML／Qt Quick（ADR-001 否決的做法）** | 場景圖由 GPU 繪製 | 重寫畫布與工具；依賴檢查掃不到 QML；測試方法要換；Presenter 多一層綁定；ADR-001 否決的理由（沒有觸控、沒有複雜動畫）沒有變 | 要先做一個最小原型才能量，成本最高 |
| **D. 調整預算，不改程式** | 例如把 I1 註明「視埠 1000×700、offscreen」，或把真實視窗的預算放寬 | 等於承認 60 fps 的目標在最壞縮放區間達不到；數字是使用者確認過的，改它是使用者的決定 | — |

## 建議（不是決定）

選 **A，並把 B 排進 S11 的第一批實驗**，理由：

1. 除了 I1 之外，本步驟量到的 UI 預算（U1a、U1b、U4、I2、I5）餘裕都大；只有 I1 在最壞縮放區間貼著線。整個工具集的重寫（C）和這個差距不成比例。
2. 瓶頸有明確的、可獨立量測的成本（細矩形的填色與呈現），B 與「縮放時快取」都是低成本的實驗；先量再決定。
3. 同時請使用者決定 D 的一部分：**I1 的預算要不要註明視埠大小與平台**（目前沒寫；1000×700 在邊緣、1600×900 與真實視窗超標）。這是預算的定義問題，不是程式問題。

## 需要使用者決定的事

1. 同意「維持 ADR-001，S11 試 B」嗎？還是現在就要換方向？
2. I1 的預算：維持 16.7 ms p95，並註明視埠 1000×700 與平台（建議 offscreen 與真實視窗各一列）？
3. 你平常用的螢幕解析度與縮放習慣是什麼？（決定 1000×700 還是 1600×900 才是代表情境。）

## 後果

- 使用者決定「維持」：ADR-001 的狀態不變，本 ADR 改成「採用：維持 ADR-001」，S11 的計畫加入實驗 B。
- 使用者決定「重審」：新增一筆取代 ADR-001 的 ADR（標明取代關係），S02 的 `ImageCanvas`／`ITool`／介面可以留用（Presenter 只依賴 `I*View`／`I*Controller`，見 ADR-001 的後果），要換的是 `ImageCanvas` 與 Item 的實作。
