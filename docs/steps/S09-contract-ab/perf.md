## 方法與限制

- **執行**：`scripts/dev/test.ps1 -Perf -Filter 'perf_compare_ui'`、`-Filter 'perf_ab'`（Release）；UI 的量測連跑 3 次（下表是範圍），另外第一次修正之後的那一次單獨列。
- **UI 的定義**（同 S02、S04）：一個動作 → 把待重繪的區域畫完（Qt 的軟體算繪，offscreen 平台，不含垂直同步與合成器）。熱機 5 次、量 30 次，中位數與 p95。比較視窗與 `ComparePresenter` 照產品的方式接；兩個 back end 是兩個假世界（同樣的格子、弱的格子不同，所以有差異），沒有執行緒池——量的只有 UI 這一側。
- **`perf_ab` 的定義**：use case 端到端（5 MP、64×32 的樣本、±5°），每個 back end 每種情境熱機 1 次、量 5 次；準確度和標準答案比（扣掉樣本框中心的固定偏移，同 T6b）；峰值記憶體是那 5 次之間行程 private bytes 的最大增量；兩個 back end 都能用時再用 `compareProposals` 比一次（兩邊的門檻都是 0.70）。
- **限制**：這台機器同一份程式在不同時間會飄 1.4–2 倍（S02–S08 都看過），所以給範圍。`perf_ab` 的情境是合成的：光照不均、低對比、模糊、反光是「像」真的，不是真的；真實影像見 §4。

讀法：
- **兩邊都找到的情境，差異只在位置**：反光時 OpenCV 偏約 0.5 px、HALCON 好（10% 反光 0.07 對 0.49）；雜訊時反過來，HALCON 偏最多 1.36 px、角度最多差 3.1°。

- **重模糊：HALCON 多出 812 個「只有 HALCON」**：551 個和已找到的元件在同一個位置（重複偵測：HALCON 的提案在同一個元件上有兩個有分數的候選），其餘多半在橫向半個格距（±42 px）的地方——相鄰兩個元件的電極被模糊成「像一個元件」，其中 242 個附近根本沒有元件（誤判）。分數 0.81–0.99，門檻擋不掉。同時 HALCON 的 use case 慢到 130–189 ms、峰值記憶體多約 80 MB。
- 以上三種（低對比的召回率、重模糊的誤判、雜訊 12 的位置 p95 0.93 px）超過 T6a／T6b，依 ADR-004 的界線**不是接受的差異**，記在 ADR-004 §5，原因與做法等使用者決定（§6）。S08 的 T6b（所有板子合在一起的 p95 0.48 px）把雜訊 12 這一塊的 p95 平均掉了。

## 6. HALCON 的補測（2026-10-12）與待處理的問題
