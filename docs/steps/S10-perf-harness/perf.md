# S10 — 效能量測紀錄

方法見 [docs/perf-test-plan.md](../../perf-test-plan.md)：熱機 5 次、正式量 30 次、看中位數與 p95；S10 起閘門用幾次執行的範圍（[ADR-023](../../adr/023-perf-regression-gate.md)）。本步驟量的是：T5（第一次）、搜尋矩陣（第一次）、harness 自己的成本、量測雜訊（行程內與跨行程）、閘門對「故意放慢」的反應；其他指標（T1–T4、T6、U1–U4、I1–I6、A/B）由既有的量測程式照舊量，數字在一鍵流程的執行紀錄與報表裡（`perf/results/`，不入版控），這裡只摘要和基準線有關的部分。

**雜訊**（`perf-compare noise`，3 次之間每個指標中位數的最大／最小差距；只算 ms 的指標、差距超過 0.05 ms 的 399 個）：**中位數 44%、p95 164%、361 個超過 15%**。第 2 與第 3 次之間：中位數 22%、p95 98%、262 個超過 15%。第 1 次整體慢 1.5–2.5 倍（UI 與 domain 的指標都是：T3、U3、I3、U4、I1、U1），OpenCV 的種子搜尋反而沒有（T2a 63–72 ms；它用 15 個執行緒，不只在釘住的那一個核心上）；第 2 次的 A/B 畫面（AB-U1a／U1b）慢 2 倍。行程內連續兩次（第 3 節的 H-noise）只差 4–27%。

**結論**：（1）S10 計畫的完成定義「量測雜訊已量化並**低於閾值**」**沒有達成**：這台機器在今天的狀態下，跨行程的雜訊遠大於 15%，而且是整台一起變慢（處理器只跑在額定速度的 54–67%）；行程內的雜訊在 15% 以內。所以閘門不用單次對預算或對一個數字，而是（a）基準線記 3 次的範圍、（b）一半以上的指標同時變慢就判 INCONCLUSIVE、（c）報表標出處理器的實際速度與負載（ADR-023）。（2）第 1 次的 T3、I3、U4-PNG、AB-U1a 超過預算、第 2 次的 U4-PNG、AB-U1a 超過，第 3 次全部在預算內（已知的 U3、I1、B1–B3 除外）；這些預算在 S04–S09 都通過過，超標是機器的狀態，不是程式變慢，**limit 沒有改**。（3）基準線 `perf/baseline/casparhsu1-harness.json` 由這 3 次建（637 個指標的中位數與 p95 範圍）；它包含一次慢的執行，所以範圍偏寬：機器狀態正常時應該重建（`perf.ps1 -Runs 3 -WriteBaseline`，開始前先關掉 Visual Studio、Chrome 與遠端桌面）。（4）第 3 次執行對這條基準線：PASS（0 回歸、627 個沒有變、0 缺少），報表嵌在 `explainer.html`。

## 5. 閘門對「故意放慢」的反應（S10 的完成定義第 2 條）

`perf.ps1 -NoBuild -Filter perf_matrix -InjectDelayMs 60`（harness 在每一次正式量測的計時區間多忙等 60 ms；產品的程式沒有改），對第 4 節的基準線比：

- 判定 **FAIL（結束碼 1）**，警告「這次執行有 60 ms 的注入延遲，不能當基準線」。
- 回歸 35 個：矩陣每一格、兩個 back end 的 `total` 都被抓到（基準格 opencv 76.1 ms 對基準線 [20.1, 26.9]，＋183%；halcon 82.3 對 [20.6, 22.6]，＋264%；25 MP opencv 128.4 對 [76.7, 99.9]，＋28%——這一格的 60 ms 只有 28%，仍然超過 15%）；另外 5 個 `template` 的階段（0.35–0.37 ms 對 0.18–0.27，差 0.1 ms，剛過 0.05 ms 的絕對下限）是這一次的雜訊，不是注入造成的（階段時間由 use case 自己量，注入在它外面）。
- 比較過的指標約 260 個、回歸 35 個（13%），低於「一半以上」，所以是 FAIL 而不是 INCONCLUSIVE；其他 400 多個指標因為 `-Filter` 沒有量，列成「缺少」。
- `perf-compare baseline` 對這份結果拒收（`injectedDelayMs` 60 > 0）；`--self-test` 另外用造的資料驗證每一條規則（20 項）。

## 結論與後續

- **量到的**：T5 第一次量（OpenCV p95 28.7–39.2 ms、HALCON 17.5–22.1 ms，預算 300，標 `calibrated`；`budgets.json` 頂層改 `calibrated`，limit 沒有改）；矩陣 15 格 × 2 個 back end 的時間、階段、峰值、準確度；harness 的開銷 0；行程內雜訊 4–27%、跨行程雜訊中位數 44%（整台變慢）。
- **閘門**：故意放慢時失敗（第 5 節）；已知的超標（U3、I1、B1–B3）列出不擋；跳過列成未驗證；一半以上變慢判 INCONCLUSIVE。基準線建了（含一次慢的執行，範圍偏寬）。
- **沒做到的**：雜訊沒有低於 15%（第 4 節的結論；是機器的狀態，不是 harness 能解決的，報表現在會把處理器的實際速度標出來）；真機視窗模式（`-Window`）有做在流程裡但**沒有跑過**；`full` profile 沒有跑過；真實影像的量測（`perf_*_real`）因為沒設 `AOI_REAL_IMAGE_DIR` 跳過。
- **給 S11 的**：OpenCV 的時間幾乎全在種子搜尋、隨角度範圍線性變大（±180° 189–271 ms）；HALCON 每次 `create_shape_model` 13–47 ms；T5 的 UI 部分 7–11 ms（物件樹約 2 ms）；U3、AB-U3 仍沒有解；基準線在機器狀態正常時重建。
- **給使用者的**：量測時關掉 Visual Studio、Chrome、遠端桌面（三次執行它們都是最忙的行程），或接受報表上的警告；要不要給 AB-U3、T7 預算仍待決定。
