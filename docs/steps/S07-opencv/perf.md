# S07 — 效能量測紀錄

原始結果：[`perf/baseline/casparhsu1-opencv.json`](../../../perf/baseline/casparhsu1-opencv.json)（入版控；`perf_opencv` 連跑 3 次的全部指標與曲線）。預算：[`perf/budgets.json`](../../../perf/budgets.json)。

**一句話**：有預算的搜尋指標**全部通過**（3 次執行）：T1 範本建立 p95 0.34–0.47 ms（預算 30）、**T2a** 5 MP 種子搜尋 p95 **67.1–72.0 ms**（預算 150）、**T4** 200 個視窗 p95 **30.5–32.7 ms**（預算 60）、**T6a** 召回率 **100%**（6 673／6 673，預算 ≥ 99%）、**T6b** 位置誤差 p95 **0.106 px**（最大 0.503 px，預算 0.5——p95 在預算內，最大值剛好超過一點點，是一個反光的元件）。第一版的 T2a、T4 超過預算，改寫精修之後（§3）才通過。use case 整條（5 MP、754 個元件、10% 缺件）66.6–70.3 ms（中位數）。使用者的真實影像（24.4 MP、12 bit）整條 113–205 ms。流程 B 每個候選類型約 8–9 ms，和類型數成正比（T7，預算待決定）。**U3 仍超標**（S04 起的已知問題，S07 沒有動它）。`perf/budgets.json` 的 limit **沒有改**，T1、T2a、T4、T6a、T6b 標成 `calibrated`。

## 方法與限制

- **執行**：`scripts/dev/test.ps1 -Preset release-opencv -Perf`（preset `perf-opencv`：所有 label `perf` 的測試，含 S02–S06 的），同一個建置連跑 3 次；環境變數 `AOI_REAL_IMAGE_DIR` 指到使用者的真實影像（`perf_opencv_real`）。S07 的量測在 `tests/backend/perf_opencv.cpp` 與 `perf_opencv_real.cpp`。
- **次數**：T1、T2a、T4 熱機 5 次、量 30 次；曲線（`A-*`、`S-*`、`P-*`）熱機 1 次、量 5 次；執行緒數（`TH-*`）熱機 2 次、量 10 次；use case 各階段（`UC-*`）跑 25 次、丟掉前 5 次；T7：N ≤ 100 量 10 次、N ＝ 1000 量 3 次；峰值記憶體 3 次。本檔的範圍是 3 次執行的最小到最大值。
- **輸入**：`tests/support/synthetic_board` 的合成板子（8 bit 灰階、雜訊 ±4、模糊半徑 1）；元件主體 56×24，樣本框外加每邊 4 像素 → **64×32**；格距 84×60，5 MP（2592×1944）約 840 個元件。T6 是 8 種情況（乾淨、雜訊、強雜訊＋模糊、5% 缺件、10% 反光、傾斜 3°、位置抖動 3 px、12 bit）。T7 的樣本庫：1000 個合成類型（主體大小與亮度各不同，第 0 個和板上的元件一樣），區域 640×480。
- **T6b 的參考點**：匹配的位置是「使用者框的樣本框中心」，它和元件真正的中心差一個固定的偏移（樣本框四捨五入到整數像素，最多半個像素）；所有元件差同一個偏移，所以 T6b 量的是扣掉這個偏移之後的誤差（`tst_opencv_end_to_end` 的 `sampleOffset`）。不扣的話，傾斜與抖動的板子會多出 0.3–0.6 px 的常數項。
- **峰值記憶體**：Windows 的峰值工作集不能歸零，所以背景執行緒每 1 ms 讀一次行程的 private bytes，取最大值減開始時的值（一次種子搜尋額外配置的記憶體，不含影像本身）。
- **執行緒**：產品的政策（`cv::setNumThreads(核心數 − 1)`，ADR-016）；`TH-*` 另外改設 1、2、4、8 個。量測衛生（`MeasurementHygiene.h`）只釘住呼叫的執行緒，OpenCV 的工作執行緒由 Windows 排程（含 E 核）。
- **沒有量**：T2b（HALCON，S08）；T5 的 UI 部分（S10）；冷的檔案快取；Debug 的速度；真實影像的召回率（沒有標準答案）；流程 B 的 UI（沒有接）。
- **限制**：這台機器同一份程式在不同時間會飄 1.4–2 倍（S02–S06 都看過），下面一律給範圍。

## 2. 預算校準

- `perf/budgets.json`：T1、T2a、T4、T6a、T6b 的 `status` 改成 `calibrated`，`measured` 寫 3 次的範圍；新增 `searchCalibrationS07`。**limit 一個都沒有改**（使用者的指示）。頂層的 `status` 維持 `proposed`（T2b、T5 還沒量）。
- 餘裕：T2a 的 p95 約是預算的一半（67–72／150），T4 約 55%（31–33／60），T1 不到 2%。
- **T7 的預算是提案，沒有寫進 `budgets.json`**（新增一個 limit 是使用者的決定）：實測每個類型 8–9 ms、線性。若 T7 定義成「區域 640×480、候選 N 個」，建議 N ＝ 10 時 ≤ 150 ms（實測 p95 87–93 ms）；N ＝ 100 時約 0.9 秒，要靠快取範本或預篩選（ADR-006 §7）才可能互動。
- 角度範圍是最大的成本因子：±180° 約是 ±5° 的 4 倍（194 對 49 ms 的中位數）；25 MP 的種子搜尋約 0.28 秒（使用者的影像是 24.4 MP）。

## 3. 改寫一次：精修的小分數圖自己算（before／after）

第一版每一層都用 `cv::matchTemplate`。同一台機器、同一個建置設定、同一組板子，各 1 次的中位數（`perf/results/opencv_20261006-184819.json` → `opencv_20261006-185223.json`，兩次都是開發中的程式，**不是最終的 3 次**）：

| 指標 | 改之前 | 改之後 | 說明 |
|---|---|---|---|
| T2a 種子搜尋（5 MP） | 193 ms（p95 263，**超過 150**） | 64 ms（p95 79） | 精修 224 → 36 ms（多執行緒的總和），頂層 35 → 33 ms |
| T4 視窗驗證（200 個） | 87 ms（p95 120，**超過 60**） | 30 ms（p95 34） | 各視窗的精修總和 972 → 167 ms |
| use case 總時間（5 MP、10% 缺件） | 228 ms | 79 ms | |
| 角度範圍 ±180° | 367 ms | 197 ms | |
| 25 MP 種子搜尋 | 1 009 ms | 297 ms | |
| 找到的元件 | — | 完全相同 | `directCorrelationMatchesOpenCv`：和 `cv::matchTemplate` 的差 < 10⁻⁴ |

原因：精修時每個候選的分數圖只有 5×5，`cv::matchTemplate` 對這麼小的圖仍走 DFT，固定成本主宰。改成 8 bit 整數點積＋積分影像（`OpenCvCorrelation`，ADR-016 §2）。

## 4. 使用者的真實影像

使用者提供的去識別化影像（**不入版控**；`perf_opencv_real`，環境變數 `AOI_REAL_IMAGE_DIR`）：5314 × 4594（24.4 MP）、16 bit 的 TIFF（LZW）、值 0..4095 → 兩個影像來源推測為 **12 bit**。HA ＝ 高角度光、LA ＝ 低角度光（大片飽和）。樣本：HA 的一根針腳（影像像素 x 442、y 444、80 × 30），兩張都用同一個框。3 次執行的結果完全相同（決定性的）。

| | HA | LA |
|---|---|---|
| 開圖（OpenCV 的來源，含 LZW 解碼；3 次） | 365–399 ms | 486–542 ms |
| 候選：樣本／種子／驗證找到／推算 | 1／1 261／2／0 | 1／1 032／49／120 |
| 種子分數 0.70–0.75／0.75–0.80／0.80–0.85／0.85–0.90／0.90–0.95／0.95–1.00 | 342／113／57／152／77／520 | 225／10／177／28／233／359 |
| 晶格 | 一維，rms 5.86 px、信心 0.28（建議檢查）、缺格 2 | 二維，rms 4.18 px、信心 0.52、缺格 169（推算 120 個） |
| 整個 use case（3 次執行 × 3 次） | 113–205 ms | 119–195 ms |

看疊圖（`real-*-overlay.png`，建置目錄，不入版控）的發現：

1. **HA 的種子分數分兩群**：≥ 0.85 的幾乎都在針腳上；0.70–0.85 的多半是焊墊的邊緣（相似但不是）。use case 的種子門檻（`seedMinScore` 0.70）與預設的分數門檻（0.70）會把它們當成找到的，晶格也因此只剩一維、信心 0.28。右上的區塊針腳的樣子不同，有一些真的針腳分數在 0.75–0.85。
2. **LA 的晶格在兩個空槽裡補了推算的缺格**（約 120 個，紅框）：S05 的已知失敗 #11（非矩形陣列），第一次在真實板子上確認。空槽邊框上還有幾個以下限 0.30 驗證「找到」的（藍框）。
3. 兩件事都在 use case 與晶格的規則（application、domain），**S07 沒有改**：要不要提高種子門檻、預設門檻，要不要讓晶格不跨過空的區域，是使用者的決定（`docs/current-status.md`）。

沒有標準答案，所以真實影像**沒有召回率與位置誤差**，只有上面的觀察。

## 5. 變異測試

一次植入一個缺陷，重建相關的測試、執行，還原後用 SHA-256 確認（腳本在 session 的暫存目錄，不在 repo）。**14 個，抓到 13 個**：

| # | 植入的缺陷 | 結果 |
|---|---|---|
| M01 | 金字塔往下換算時忘了 −0.5 | `tst_opencv_backend` |
| M02 | 範本轉反方向 | `tst_opencv_backend` |
| M03 | 不做次像素內插 | `tst_opencv_backend`、`tst_opencv_end_to_end` |
| M04 | 轉灰階時不看有效位元數 | `tst_opencv_backend`、`tst_opencv_end_to_end` |
| M05 | 覆寫值比資料小也接受 | `tst_image_view`、`tst_presenter` |
| M06 | 換影像時忘了位元數的設定 | `tst_document`、`tst_presenter` |
| M07 | 配方 v1 → v2 的遷移什麼都不做 | `tst_recipe_store` |
| M08 | 不過濾區域外的匹配 | `tst_opencv_backend` |
| M09 | NCC 的變異數忘了減平均 | `tst_opencv_backend`、`tst_opencv_end_to_end`、`tst_opencv_library_matcher` |
| M10 | 參考影像不縮放成板子的比例 | `tst_opencv_library_matcher` |
| M11 | **拿掉角度的爬坡** | **存活**：加了 ±5°、±30° 的角度掃描測試仍存活，誤差完全相同（0.424°、0.213°）。第 0 層「兩側沒比過就補比」已經足夠；爬坡留著當防禦（上一層的估計差兩步以上時才有作用，沒有重現過） |
| M12 | 角度不夾回範圍內 | `tst_opencv_backend` |
| M13 | 開新影像時不套用位元數的設定 | `tst_presenter` |
| M14 | 精修時忘了區域的原點 | `tst_opencv_backend` |

角度掃描（M11 之後加的測試）的發現：48×28 的範本、±5° 每 0.5° 一組，角度最大誤差 **0.42°**（第 0 層步進 2°，約 0.2 步；範本角落位移 0.21 像素）。原因是 NCC 對角度的曲線在真值兩側不對稱（真值 +1° 時 −1°、+3° 的分數是 0.981、0.966），拋物線的頂點偏向 0°。試過「每個角度用自己的次像素峰值再內插」，最大誤差只從 0.424° 降到 0.411°，沒有採用。
